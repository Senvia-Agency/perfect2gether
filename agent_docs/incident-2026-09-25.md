# Supabase recurring timeouts — 25 September 2026

## Evidence (UTC)

- 24 September 18:10: internal Realtime catalog queries start timing out;
  cron startup and exporter queries subsequently fail too.
- 25 September 08:05: 164 gateway requests in one minute; 21 the next minute,
  then approximately two per minute. Realtime initialization creates partitions
  and triggers two successful PostgREST schema reloads (~1.0–1.4 seconds).
- 08:13: cron jobs cannot start. By 08:16 even the exporter reading
  `pg_stat_activity` times out. This is not just a failing CRM query or login UI.
- 09:55: controlled restart requested; DB startup 10:00, services healthy ~10:01.
- Read-only checks after recovery: 259 clients, 6 proposals, 6 sales in P2G;
  no evidence of deleted business records. Pool maximum from PostgREST logs: 10.
- No observed OOM kills, deadlocks, exhausted disk or retained-WAL backlog.
  Current instance has ~406 MiB RAM, ~198 MiB available at a later sample, and
  ~305 MiB swapped. Swap alone does NOT establish memory exhaustion; neither
  does committed virtual memory exceeding the reported commitment threshold.

## Confirmed application defects and fixes

1. Every dashboard widget mounted an unused ecommerce statistics query with
   minute polling. Removed in e84d41a, including ecommerce widget definitions.
2. `get-team-members` called Auth twice per member (user + MFA). P2G has seven
   active members, so each invocation added 14 Auth requests. Replace these
   with one service-role-only SQL read returning the same ban/MFA booleans.
   Keep requester authentication and organization checks unchanged.
3. The function reported an upstream Auth outage as 401, causing the caller to
   refresh a valid token and retry. Return 503 for upstream availability errors.
4. Repeatedly mounted filters/widgets considered successful reads immediately
   stale. Reuse core list data for 30 seconds and team/pipeline data for 60
   seconds. Existing mutation/Realtime invalidations still refresh immediately.

## Limits and next diagnostic step

These are proven request amplification defects, not proof of the sole cause of
the whole PostgreSQL outage. Most failure-time process/wait information was not
available because even trivial management SQL timed out. Statistics reset on
restart; current query timings cannot establish which query caused a past stall.

No plan upgrade, instance sizing change, security relaxation, business data
deletion, managed event-trigger change or automatic restart policy is applied.
Historical cron logs are retained. If the whole DB stalls again after these
fixes, capture provider-side process/wait and host IO/memory diagnostics through
Supabase support with the UTC windows above, before attributing it to data size.

## CPU indicator discrepancy (read-only verification)

- 11:41 UTC: reproduced `CPU 97%` in the project's home infrastructure card.
- The detailed Database report opened from that card showed 3.33% for the
  preceding hour. The public Studio implementation uses `avg_cpu_usage` for
  the card and separate busy/idle series for the detailed report; those are
  distinct inputs. The backend aggregation semantics were not verified.
- Two direct Prometheus counter samples from 11:42:44 to 11:43:50 UTC recorded
  131.65 aggregate CPU seconds: 98.071% idle, 0.957% iowait, 0.972% processing.
  Load1 was 0.09 and Load5 0.12. DB, REST and Auth health checks passed.
- The first 30-second attempt returned identical cached counters and was
  discarded; it does not count as a valid utilization measurement.
- This establishes inconsistent indicators, not proof that historical outages
  did not occur or that the home card is definitively displaying inverted idle.

## Additional resilience changes

- Treat PostgREST plain-object auth/permission errors as non-retryable.
- Limit transient availability failures to one retry, spaced 5–7.5 seconds
  with jitter instead of three synchronized retries. No mutation retry added.
- Failed module reads throw instead of saving generic defaults as success;
  seed from the organization already loaded by Auth. Preserve cached settings.
- Client labels fall back to the successfully loaded Auth organization while
  the secondary organization query is unavailable.
- Client type aggregation fails atomically if proposals, sales or CPE reads
  fail, preserving an existing good map instead of caching a partial result.
- Reuse organization/modules for 60 seconds and client types for 30 seconds.
- Regression tests cover plain-object auth errors, bounded retries, backoff,
  successful empty reads, failed partial reads, cached data preservation,
  recovery, and cache-key separation by organization. Build passed.

No database schema/data/configuration change was made for these protections.
These changes mitigate failure impact and request amplification; they are not
a demonstrated fix for the provider-wide PostgreSQL stalls.
